Why Semantic Layouts

Vanilla Breeze layout primitives work on any element, not just custom elements. Putting them on the semantic HTML you already have gives you the same layouts with fewer wrappers.

  • Fewer Nesting Levels

    Combine center + gap on a single element instead of nesting center inside stack. Less indentation, easier to scan.

  • Real Semantics

    The layout lives on the element that already carries meaning: <nav>, <article>, <ul>. A <layout-stack> wrapper is a generic box to assistive technology.

  • LLM-Friendly Markup

    Standard HTML elements are what tools and models know best. Your code is easier to read for both humans and machines.

  • Same CSS Rules

    Each layout is defined once for both forms, as :is(layout-stack, [data-layout="stack"]). The host element still matters: see What differs.
Key Insight Semantic layouts are not a replacement for custom elements. They are an alternative authoring approach. Both are fully supported and share the same layout rules.

What Differs Between the Forms

The layout rules are shared, but the attribute form inherits everything about its host element.

  • Containers. VB makes every main, article, section and aside a size-query container (container-type: inline-size). A <section data-layout="stack"> is therefore a container, while a <layout-stack> is not. Container queries and cqi units inside it measure the section, not the page.
  • Content-sized children. A container has no intrinsic width. Where a layout sizes its children by their content (cluster, reel, centred cover, a stack aligned start/center/end), a sectioning child would collapse to zero width, so VB switches containment off for those children. Add data-container (and give the child a width) to keep one on purpose.
  • Element defaults. The host keeps its own styles: a ul keeps its bullets (add class="unstyled"), a nav or header keeps any VB styling for that element.
  • Semantics. The host keeps its role. <layout-*> elements have none.

The Center + Gap Pattern

The most common refactoring: eliminating a nested stack inside a center element.

In Vanilla Breeze, when data-layout-gap is added to a center element, the center switches from display: block to display: flex; flex-direction: column with the specified gap. This means a single element can both center its content and space its children vertically.

    • When to Keep Custom Elements

    Not everything should become a data attribute. Visual components stay as custom elements.

    The key distinction is between layout primitives and visual components:
    • Layout primitives (stack, cluster, grid, center, cover, sidebar, switcher, reel, columns, prose) control spacing and arrangement. These are good candidates for data-layout attributes.
    • Visual components (card, badge, brand-mark, form-field) provide visual styling like shadows, borders, backgrounds, and typography. These stay custom elements. The canvas surface is the exception: it has an attribute form, data-canvas.

    Decision Guide

    Use this table to decide which approach fits your situation.

    Scenario Recommended Approach Why
    Quick prototyping Custom elements Fastest to type, self-documenting tag names
    The right element already exists (nav, ul, article) Data attribute on it No extra wrapper; the element keeps its meaning
    You need a generic wrapper anyway Custom element A <layout-*> element is a clearer wrapper than a <div>
    Complex nested layouts Data attributes Combining layout and meaning on one element reduces nesting depth
    Content-sized children that must be query containers Either, plus data-container See What differs
    Working with LLMs or AI tools Data attributes Standard HTML is better understood by AI
    Visual components (card, badge) Custom elements These provide styling, not just layout
    Teaching layout concepts Custom elements Tag names make the layout intent explicit

    You can freely mix both approaches in the same page. Use custom elements where they make the code clearer and data attributes where they reduce unnecessary nesting.

     Bottom Line There is no wrong choice. Both forms apply the same layout rules; the attribute form also brings its host's semantics and, on main, article, section and aside, container-query containment. Choose whichever makes your HTML most readable for your team and your tools.

    Page Layouts & Grid Identity

    Semantic layouts extend beyond component-level patterns to full page structure with the grid identity system.

    At the page level, data-page-layout on <body> places <header>, <nav>, <main>, <aside> and <footer> into named grid areas automatically — no classes needed. It is the only page-template system; data-layout lays out components inside it.

    At the component level, data-layout="regions" generalizes the header/content/footer pattern to any element, and data-layout="media" provides a figure+content media object. These compose with page layouts.

    Accessibility

    • Landmarks come from elements, not layouts. main, nav and aside are landmarks wherever they are; header and footer are banner and contentinfo landmarks only when they are not inside an article, aside, main, nav or section. A section is a region landmark only when it has an accessible name (aria-labelledby pointing at its heading). An unnamed section, or a header inside a section, gives document structure but is not a landmark.
    • Keep DOM order meaningful. Layouts change visual position (reversed media objects, switchers, mobile collapse of sidebars). Keyboard and screen-reader order follow the DOM, so write the source in reading order.
    • Lists for lists. Putting a grid or cluster on a ul or menu lets screen readers announce the number of items.
