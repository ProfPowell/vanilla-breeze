The Concept

VB's grid identity system implements the CSS Zen Garden principle: the same semantic HTML transforms through pure CSS. Write <header>, <nav>, <main>, <aside>, and <footer>, and the layout assigns them to grid areas automatically.

Zen Garden Principle HTML declares structure. CSS assigns layout. JavaScript handles behavior. Each concern stays in its proper layer.

Three Tiers

Grid identity works at three levels, each scoped to a different container:

  • Tier 1: Page

    data-page-layout

    Body-level structure. Areas: body-header, body-nav, body-main, body-aside, body-footer (plus hero, feature, cta in landing)

  • Tier 2: Main

    main[data-layout="sidebar-left|sidebar-right"]

    A sidebar inside the content area. Areas: main-nav, main-article, main-aside

  • Tier 3: Component

    data-layout="regions"

    Generalized structure on any element: header first, footer last, everything else in between

Page-Level Identity

Apply data-page-layout to the <body> element. Direct semantic children are auto-assigned to grid areas based on their element type. It is VB's only page-template system; the full reference (modifiers, mobile drawer, accessibility) is on the attribute page.

A bare data-page-layout (no value) uses the stack template. The --tpl-* tokens are declared on the [data-page-layout] host, not on :root: to replace a template, set the token on the host (for example body { --tpl-sidebar-left: …; }).

Content-Aware Adaptation

Layouts automatically adapt when elements are absent. CSS :has() selectors detect what children are present and adjust the grid template accordingly.

  • sidebar-left without <nav> → single column
  • sidebar-right without <aside> → single column
  • holy-grail without <aside> → two columns (nav + main)
  • holy-grail without <nav> → two columns (main + aside)
  • holy-grail without both → single column

Named Area Overrides

Use data-layout-area to place a child of a page layout in a named area. Only the landing template defines extra areas, so these are the values that work:

Value Use Case
heroHero section on landing pages
featureFeature showcase section
ctaCall-to-action section

An area name that the active template does not define creates an implicit, zero-width grid track, so the child disappears. Use the semantic elements (<nav>, <aside>, …) for the standard regions instead.

Main-Level Identity

A <main> with data-layout="sidebar-left" or data-layout="sidebar-right" creates a second tier of grid identity. Only these two values assign main-* areas, and only to direct nav, article and aside children.

Main-level templates also support :has() adaptation: if the nav or aside is absent, the layout falls back to a single column. Below 48rem (unless data-layout-nowrap is set on the main) they stack in the order article, aside, nav, so a leading <nav> moves below the article visually while staying first in the reading order.

Other children of these mains (a <header>, <section> or <footer>) get no area and are auto-placed. For a header/content/footer structure, use regions on an inner element (below).

Component-Level Regions

Two layouts extend the idea down to individual components. Both are component layouts that work on any element, and both place children by element type rather than by named areas.

Regions

data-layout="regions" arranges any element as a header / content / footer column. Semantic children find their place without extra attributes.

Child Placement
<header> or [slot="header"]First
<section> or [slot="content"]In DOM order; grows to fill the free space
<footer> or [slot="footer"]Last. With no <section> to take the free space, it is pushed to the bottom of an equal-height card
Any other childBetween header and footer, in DOM order

The header and footer are moved visually with order; put them first and last in the source too, so the reading order matches.

Composing Tiers

The full power of grid identity appears when you nest all three tiers. Each tier is scoped to its own container, so area names never collide.

In this example:

  • Tier 1 — data-page-layout="sidebar-left" on body places the header, nav, main, and footer into page-level grid areas.
  • Tier 2 — data-layout="sidebar-right" on main creates a secondary sidebar for the table of contents, using main-article and main-aside areas.
  • Tier 3 — data-layout="regions" on article places its header first, the section in the middle and the footer last.
No collisions The page and main tiers use namespaced area names (body-*, main-*), and the component tier places by element type, so they compose freely without conflict.

Named Containers

Page layout regions have named containers for targeted @container queries. This lets component authors write precision queries that target a specific region rather than the nearest anonymous container.

Context Element Container Name
data-page-layout<main>region-main
data-page-layout<nav>region-nav (only where the nav column has a definite width; see data-page-layout)
data-page-layout<aside>region-aside
main[data-layout="sidebar-left"]<nav>region-main-nav (a nav is not a size container by default; add data-container to query it)
main[data-layout="sidebar-left"]<article>region-main-content
main[data-layout="sidebar-right"]<article>region-main-content
main[data-layout="sidebar-right"]<aside>region-main-aside

Example: adapt typography when the main content area is narrow:

@container region-main (width < 40rem) { .article-grid { grid-template-columns: 1fr; } }

    Accessibility

    • Grid placement changes where regions appear, not their order in the DOM. Keyboard and screen-reader order follow the source, so write header, nav, main, aside, footer in reading order.
    • The page regions are landmarks because of their elements (main, nav, aside, and header/footer as direct children of body), not because of the grid. Give each nav and aside an aria-label when there is more than one.
    • Collapsed mobile layouts and the dashboard drawer are covered on data-page-layout.
