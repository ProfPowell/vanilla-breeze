When to Use

  • Form validation messages (see form-field)
  • Calculated totals or results
  • Dynamic values that change based on user input
  • Displaying range slider values
  • Any result that is derived from other form controls

Why Output over div/span?

The <output> element is purpose-built for displaying results of calculations and user actions. It has three advantages that <div> and <span> lack:

  • Semantic meaning: Browsers and assistive technology understand that output contains a computed result
  • A live region by default: Output has the implicit role status, which carries aria-live="polite" and aria-atomic="true", so screen readers announce the whole new value when its content changes
  • Labelable and form-associated: A <label for> names it, form.elements lists it, and form.reset() restores its default value
  • for attribute: Records which inputs produced the result (readable from script as output.htmlFor). Browsers do not expose this relationship to assistive technology; use aria-describedby or aria-controls for that
Approach Semantics Accessibility Recommendation
<output> Result of action Implicit status live region, labelable Recommended
<span class="error"> None Requires manual ARIA Avoid
<div class="message"> None Requires manual ARIA Avoid

Four CSS classes control presentation:

Class Effect
(default) Inline monospace with subtle raised background
.block display: block with larger padding for full-width output
.inline No padding or background — blends into surrounding text
.highlight Brand-tinted background with interactive color text
.large Increased font size (var(--font-size-xl)) for prominent values
Default Block output Inline Highlighted Large

Variants can be combined: class="large highlight" or class="block success".

State Variants

Semantic colors for different message types. Each state pairs a subtle tinted background token (--color-success-subtle, --color-warning-subtle, --color-error-subtle) with its matching text token, so they follow light/dark mode and themes. Color is not the only signal: the text itself must say what happened. In forced-colors mode the tints are dropped and every chip gets a system-color border instead.

Class Use Case
.success Confirmations, completed operations (green tones)
.warning Caution messages, pending review (amber tones)
.error Validation errors, failures (red tones)

Inside form-field, output.hint and output.error are messages, not results: they skip the monospace chip and take form-field's small message styling. The same applies to output.error-summary, checkbox-group outputs, and the data-empty / data-loading / data-error feedback outputs.

Live Status Updates

An output is already a polite live region, so status text written into it is announced without extra ARIA. Keep the element in the page from the start and change its content; a live region inserted at the same moment as its text is often not announced.

Accessibility Notes

  • Implicit role="status": Changes are announced politely and atomically (the whole content is re-read). No aria-live is needed
  • Silence chatty outputs: For values that change on every keystroke or slider step, set aria-live="off" — the control already announces its own value
  • Name it with a label: <label for="output-id"> gives the output an accessible name; don't wrap a control and its output in one label
  • for is not an ARIA relationship: Browsers don't expose it to assistive technology
  • Link with aria-describedby: Connect inputs to their validation outputs so screen readers announce the message when the input is focused
  • Don't use for static content: Output is for dynamic/calculated values
  • Include meaningful content: Always have useful text, not just icons

CSS Reference

Message outputs (form-field hints and errors, the error summary, checkbox-group and feedback-state outputs) are excluded from all of these rules.

output:where(:not( [data-empty], [data-loading], [data-error], .hint, .error-summary, form-field .error, :is(fieldset[data-min-checked], fieldset[data-max-checked]) > output )) { display: inline-block; font-family: var(--font-mono); font-variant-numeric: tabular-nums; padding: var(--size-2xs) var(--size-xs); background: var(--color-surface-raised); border-radius: var(--radius-s); /* An empty output (a result not computed yet) collapses to nothing instead of rendering a blank chip. */ &:empty { padding: 0; background: transparent; } /* --- Output Variants --- */ /* Block output */ &.block { display: block; padding: var(--size-s) var(--size-m); } /* Inline output (minimal) */ &.inline { padding: 0; background: transparent; } /* Highlighted output */ &.highlight { background: color-mix(in oklab, var(--color-interactive) 10%, transparent); color: color-mix(in oklab, var(--color-interactive) 70%, var(--color-text)); } /* Large output (for prominent results) */ &.large { font-size: var(--font-size-xl); padding: var(--size-s) var(--size-m); } /* --- Output States --- */ &.success { background: var(--color-success-subtle); color: var(--color-success-text); } &.warning { background: var(--color-warning-subtle); color: var(--color-warning-text); } &.error { background: var(--color-error-subtle); color: var(--color-error-text); } /* Forced colors drop the tinted backgrounds, so the chip and the state variants would vanish into the text.
