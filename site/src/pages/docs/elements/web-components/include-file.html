Overview

The <include-file> component fetches a same-origin HTML fragment, sanitizes it, and inserts it. Any existing content serves as a fallback shown until the fetch completes (or if it fails).

Security & Nesting

<include-file> is safe by default. Each relaxation is an explicit attribute the page author writes; content can never grant itself trust.

Same origin by default

src is resolved against the page (document.baseURI). Only http:/https: URLs on the page’s own origin load. blob:, data:, javascript: and other schemes are always refused, and a same-origin URL that redirects to another origin is refused too. Add allow-cross-origin to load from another origin; that server must also allow it with CORS.

Sanitized by default

Fetched HTML goes through the shared VB sanitizer before it is inserted. It removes <script>, <iframe>/<object>/<embed>, <form>, <base>, <meta>, <link>, SVG <foreignObject>, every on* event handler, srcdoc, javascript: and data: URLs on links and loaders, and script-bearing style. Nested <include-file> elements keep their src but lose trusted, allow-scripts and allow-cross-origin, so they stay same-origin and sanitized. The sanitizer is not a full HTML policy engine: it blocks script execution, not styling or layout tricks.

trusted and allow-scripts

Set trusted when you control the source and need markup the sanitizer removes (forms, inline handlers, iframes). Scripts in the fragment run only with both trusted and allow-scripts; allow-scripts alone is ignored with a console warning. Each load runs only that fragment’s scripts, once; author scripts and earlier appended content are never re-run or removed. Never use trusted on a URL that serves user-generated content.

Cycles and depth

Fragments may contain further <include-file> elements. An include whose URL already appears among its ancestor includes (a fragment including itself, or A → B → A) is refused, as is nesting deeper than 10 levels. Both show the normal error state.

Relative URLs inside fragments

The fragment is parsed into the host page, so relative URLs inside it (links, images, nested src) resolve against the host page, not against the fragment’s own URL. Use root-relative URLs (/partials/…) in fragments that are included from more than one place.

Progressive Enhancement

Without JavaScript, the fallback content (whatever HTML is inside the element) remains visible and the src URL is never fetched. Make the fallback useful on its own, for example a link to the full page the fragment comes from, so nothing is silently missing.

Accessibility

  • Fallback content ensures content is always available.
  • aria-busy="true" is set while a fetch is in flight.
  • Content that changes after load (a src change or reload()) is not announced by default. Add aria-live="polite" to the element to opt in.
  • On failure the original fallback is restored (first load, replace mode). When no fallback remains, an error message renders as a real role="alert" paragraph; set its text with data-label-error.
