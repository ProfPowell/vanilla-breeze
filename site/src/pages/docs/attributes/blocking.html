Overview

The blocking attribute holds the first paint until a resource has loaded. Its only value is render.

Many resources already block rendering without it. A stylesheet that the parser finds in <head> (when its media matches), a <style> in <head>, and a classic <script> in <head> without async, defer or type="module" all block. Adding blocking="render" to them changes nothing.

The attribute matters for resources that would not block on their own:

  • <script type="module">, which is deferred by default
  • <script async> and <script defer>
  • <link>, <style> and <script> elements inserted into <head> by script
  • <link rel="preload"> and <link rel="modulepreload">

Values

ValueBehavior
renderDo not paint until this resource has loaded (for scripts: loaded and run)

Applies to: <link>, <style>, <script> (in <head>)

A stylesheet inserted by script

Stylesheets that script adds to <head> do not block rendering. Set the attribute when the page must not paint without them, for example a theme chosen from saved preferences:

const link = document.createElement('link'); link.rel = 'stylesheet'; link.href = `/themes/${savedTheme}.css`; link.blocking = 'render'; document.head.append(link);

This only helps while the browser is still before its first paint, so the script has to run early: a classic or blocking="render" script in <head>.

When to use blocking="render"

  • Theme initialization: a module or async script that applies the user's theme or color scheme, so they never see one frame of the defaults.
  • Script-inserted critical CSS: a stylesheet chosen at runtime that the page cannot be shown without.
  • A/B tests and personalization: async scripts that change above-the-fold content, to avoid a visible swap.

Loading CSS Without Blocking

The reverse question comes up more often: how do you load CSS that the first paint does not need? A plain <link rel="stylesheet"> in <head> always blocks, so leaving blocking off is not enough. These patterns avoid blocking:

  • A non-matching media: stylesheets whose media query does not match are downloaded at low priority and do not block. This suits print styles and styles for viewports the reader is not using.
  • Insert it from script: a stylesheet that your module script adds after load does not block. Pair it with rel="preload" so the download starts early.
  • Link it in <body>: a stylesheet linked just before the content that needs it blocks only the content after it in Chromium and Firefox, not the content above it.
const link = document.createElement('link'); link.rel = 'stylesheet'; link.href = '/css/comments.css'; document.head.append(link);

Without JavaScript the inserted stylesheet never loads, so only use this for CSS the page works without.

Limitations

  • Browser support: Chromium-based browsers support blocking since version 105. Check current support for Firefox and Safari. Browsers that do not support it ignore the attribute, so the resource loads with its default behavior.
  • Only "render" is defined: the spec allows for future tokens, but render is the only one today.
  • Performance tradeoff: every render-blocking resource delays first paint. Overusing blocking="render" hurts Core Web Vitals (FCP, LCP).
  • Does not change execution order: for scripts it holds the paint, not the parser. Use defer or type="module" if you also need ordered execution after parsing.
  • Head only: render-blocking applies to elements in <head>. Once the first paint has happened, the attribute has no effect.
