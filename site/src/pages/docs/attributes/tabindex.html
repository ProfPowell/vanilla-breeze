Overview

The tabindex attribute decides whether an element can receive keyboard focus and whether Tab stops on it. Links with href, buttons and form controls are focusable already. You need tabindex for the few other things that must take focus: a scrollable region, a heading you move focus to after an action, or the items of a composite widget.

Applies to: every element (it is a global attribute).

Absent, "" or not an integerThe element's default: focusable if it is natively interactive, otherwise not.—

Natively focusable without tabindex: <a href>, <button>, <input>, <select>, <textarea>, <summary>, <iframe>, media with controls, and contenteditable regions.

Examples

Skip link

A skip link is the first focusable element on the page and jumps past the header. Following a fragment link already moves the sequential focus starting point, so tabindex="-1" on the target is optional. Adding it makes the target itself take focus, which helps some screen readers announce where the user landed. Hide the link with VB's skip-link recipe, which shows it on focus. Do not use .visually-hidden: that keeps a focused link invisible.

Focus after removing content

When the focused element disappears, focus falls back to the page body. Move it somewhere sensible: the next item, or a heading with tabindex="-1".

const list = document.getElementById('tasks'); const heading = document.getElementById('tasks-heading'); // tabindex="-1" list.addEventListener('click', (event) => { const button = event.target.closest('button'); if (!button) return; const item = button.closest('li'); const next = item.nextElementSibling || item.previousElementSibling; item.remove(); (next?.querySelector('button') ?? heading).focus(); });

Roving tabindex

In a toolbar, tab list or grid, only one item is a Tab stop (0); the others are -1. Arrow keys move focus and move the 0 with it. Tab leaves the widget in one press.

 const toolbar = document.querySelector('[role="toolbar"]'); const buttons = [...toolbar.querySelectorAll('button')]; toolbar.addEventListener('keydown', (event) => { const i = buttons.indexOf(document.activeElement); const step = { ArrowRight: 1, ArrowLeft: -1 }[event.key]; if (i === -1 || !step) return; const next = buttons[(i + step + buttons.length) % buttons.length]; buttons.forEach((b) => { b.tabIndex = -1; }); next.tabIndex = 0; next.focus(); event.preventDefault(); });

VB components that need this pattern already implement it; see below.

In Vanilla Breeze

  • Scroll regions are your job. A data-table-scroll wrapper and a data-layout="reel" region without focusable children need tabindex="0" plus a name (aria-labelledby or aria-label) so keyboard users can scroll them.
  • Components manage tabindex for you. Roving tabindex is built into <tab-set>, <context-menu>, <drop-down>, <page-tools>, <selection-menu>, <emoji-picker> and the date and calendar components. Do not add your own tabindex to their internals.
  • Focus styles. VB draws :focus-visible rings for links, buttons, form controls and summary (for example src/native-elements/button/styles.css). There is no VB rule for an arbitrary element with tabindex: it gets the browser's default focus ring. Do not remove it with outline: none.
  • data-focus-trap keeps Tab inside a region and restores focus when it closes, without you editing tabindex values.

Accessibility

  • Prefer the native element. A <button> brings focus, Enter/Space activation and the button role. tabindex="0" on a <span> brings only focus.
  • A focus stop needs a role and a name. Without them the element is announced without a meaningful role, so users do not know what it is.
  • A focus stop needs keyboard handling. If it does something on click, it must do the same on Enter (and Space for buttons).
  • Do not use tabindex="-1" to "disable" a control. It still responds to clicks and is still announced as usable. Use disabled, aria-disabled="true" (when it must stay discoverable; see ARIA states), or inert on a whole region.
  • Keep visible focus. WCAG 2.4.7 requires a visible focus indicator on everything that can take focus.

Gotchas

  • Scroll containers. Chrome 130 and later, and Firefox, make a scrollable region keyboard-focusable on their own when it contains nothing focusable. Not every browser does, so keep tabindex="0" (and a name) on scroll regions.
  • Positive values pull elements ahead of the whole page, including third-party widgets, and must be renumbered every time content changes.
  • tabindex="-1" on a native control takes it out of the Tab order but leaves it clickable and announced. That is rarely what you want.

Which to choose

  • A native element — anything clickable. No tabindex needed.
  • tabindex="0" — a scroll region, or a custom widget with role and keyboard support.
  • tabindex="-1" — a place you move focus to with script.
  • disabled, aria-disabled, inert — making something unavailable.
