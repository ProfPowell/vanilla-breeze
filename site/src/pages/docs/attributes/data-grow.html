Overview

data-grow on a <textarea> makes it grow with its content and shrink back when text is removed. It starts at rows lines and, with data-max-rows, stops growing at that many lines and scrolls. Browsers with field-sizing: content do the sizing in CSS; elsewhere a script measures scrollHeight.

Usage

With field-sizing (CSS path)

  1. CSS sets field-sizing: content and resize: none on textarea[data-grow], so the textarea grows even before the script runs.
  2. The minimum height is rows lines plus padding and border (field-sizing itself ignores rows, and VB's usual 8rem textarea minimum does not apply).
  3. With data-max-rows, max-block-size is that many lines plus padding and border; past it the textarea scrolls.
  4. The script only writes --grow-rows and --grow-max-rows and marks the textarea data-grow-init="". Programmatic values resize on their own.

Without field-sizing (JavaScript fallback)

  1. The textarea is marked data-grow-init="fallback"; only this path hides overflow and the resize handle.
  2. On input, change and after a form reset, the height is set to auto and then to scrollHeight plus the border, so it shrinks as well as grows.
  3. With data-max-rows the height is capped at that many lines plus padding and border, and overflow-y switches to auto past the cap.

Options

AttributeValuesDefaultEffect
data-grow boolean — Turns auto-grow on.
rows number 2 Native attribute. The starting and minimum height in lines; the textarea never shrinks below it.
data-max-rows positive number no cap Lines after which the textarea stops growing and scrolls. 0 or an invalid value means no cap.
data-grow-init set by the script — "" on the CSS path, "fallback" on the JavaScript path. Do not set it yourself. It is not the double-binding guard, so a cloned textarea (which copies it) is still wired.

Events

No custom events. The fallback listens for input and change. Setting .value from script fires neither: with field-sizing the height follows anyway, but for the fallback (and for a data-count counter on the same textarea) dispatch an input event afterwards. Form resets are handled for you.

textarea.value = savedDraft; textarea.dispatchEvent(new Event('input', { bubbles: true }));

Styling

No public custom properties: --grow-rows and --grow-max-rows are written by the script from rows and data-max-rows; set those attributes instead. The shipped rules:

/* native-elements/input/styles.css: start at rows, not 8rem */ textarea[data-grow] { min-block-size: calc( var(--grow-rows, 2) * 1lh + 2 * var(--input-padding-inline, 0.5rem) + 2 * var(--border-width-thin, 1px) ); } /* web-components/_shared/form-enhancements.css */ @supports (field-sizing: content) { textarea[data-grow] { field-sizing: content; resize: none; } textarea[data-grow][data-max-rows] { max-block-size: calc( var(--grow-max-rows, attr(data-max-rows type(), 999)) * 1lh + 2 * var(--input-padding-inline, 0.5rem) + 2 * var(--border-width-thin, 1px) ); overflow-y: auto; } } /* JavaScript fallback only */ textarea[data-grow][data-grow-init="fallback"] { overflow: hidden; resize: none; }

Without JavaScript

  • With field-sizing support the textarea still grows. Its minimum is two lines (the script is what reads rows).
  • data-max-rows still caps it in browsers that support typed attr(), which read the attribute directly; in others the textarea grows without a cap.
  • Without field-sizing support it keeps its rows height and the native resize handle.

Accessibility

  • The native <textarea> is untouched, so labels, keyboard use and screen-reader support are unchanged.
  • Growing shows all text without an inner scrollbar, which helps users who zoom or have trouble with nested scrolling. Past data-max-rows the textarea scrolls like any other.
  • The resize handle is removed while the textarea sizes itself; set a generous data-max-rows (or none) so long text stays readable.
