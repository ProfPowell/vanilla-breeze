Overview

data-page-layout turns the page into a CSS grid where the semantic elements are the grid items: <header>, <nav>, <main>, <aside> and <footer> auto-register to named areas. The semantic markup you already have IS the layout.

It is VB's only page-template system. Use it on <body>; the rules are not body-scoped (except the wide-screen cap), so the same templates also work on a <section> — which is how the demos below preview them.

The children land in body-header, body-nav, body-main and body-footer automatically. Only direct children are placed.

Page layout vs data-layout

  • data-page-layout shapes the page: which region goes where, how they collapse on small screens. One per page, on <body>.
  • data-layout lays out a component: the children of any element (a stack inside <main>, a cluster in a <nav>, a grid of cards). Use it inside the page regions.

data-layout="holy-grail" and data-layout="dashboard" no longer exist: they were a second copy of these templates with different area names and widths. Use data-page-layout="holy-grail" / "dashboard". data-layout="regions" stays: it structures a component (a card's header/content/footer), not a page. For a sidebar inside the main region, use <main data-layout="sidebar-left|sidebar-right"> (see Grid Identity) or <layout-sidebar>.

A child whose area the template does not define (an <aside> in sidebar-left, app-shell or dashboard; a <nav> in sidebar-right; a <footer> in app-shell or dashboard) gets an implicit grid track beside the template and lands out of place. Pick the template that has a slot for every region you use.

Small screens, wide screens and print

  • Below 48rem, sidebar-left, sidebar-right and holy-grail collapse to the stack shape (header, nav, main, aside, footer). app-shell moves its nav below the main region as a bottom bar, with safe-area padding for notched devices. dashboard drops its nav column and turns the nav into a drawer. data-layout-nowrap on the host opts out of all of these.
  • At 87.5rem and wider, body[data-page-layout="holy-grail"] and body[data-page-layout="dashboard"] stop growing and centre.
  • Print: the grid becomes a single block, and the nav and aside regions are hidden.

Dashboard drawer

Below 48rem the dashboard nav is an off-canvas drawer: fixed to the inline-start edge, full height, as wide as the sidebar width (16rem by default) or 85vw, whichever is smaller. Open, it covers the header too, toggle included. While closed it is visibility: hidden, so its links are out of the tab order and the accessibility tree, not just moved off-screen. It slides in when it opens (instantly with reduced motion), from the right in right-to-left pages. An element with data-nav-toggle inside the layout is hidden at 48rem and wider, where the nav is a normal column.

No script: a native popover

Give the nav popover and an id, and point a button at it. The browser handles opening, Escape, light dismiss and focus return; from 48rem the nav renders as a normal column despite the popover attribute.

Named areas

data-layout-area places a direct child in one of the extra areas of the landing template: hero, feature or cta. No other template defines extra areas; an area name the active template lacks creates an implicit zero-width track and the child disappears.

App shell

app-shell puts a vertical nav bar beside the header and main region, and moves it to a bottom tab bar on small screens.

Container queries

The regions carry container names so component CSS can adapt to the region it sits in:

  • <main> → region-main
  • <aside> → region-aside
  • <nav> → region-nav, where the nav column has a definite width: stack, sidebar-left, holy-grail, landing, and dashboard with data-layout-sidebar-width or data-sidebar="collapsed". In app-shell, a default dashboard and nav.bottom the nav is sized by its content, and making it a size container would collapse it.
@container region-aside (width < 16rem) { .product-card { /* compact variant */ } }

For containers anywhere else, see data-container.

Accessibility

  • Landmarks come from the elements. As direct children of <body>, header and footer are the banner and contentinfo landmarks, and main, nav and aside are main, navigation and complementary. Name each nav and aside with aria-label when there is more than one. A section placed with data-layout-area is a region landmark only when named (aria-labelledby).
  • Reading order is source order. Grid placement does not change keyboard or screen-reader order. Write regions in reading order (header, nav, main, aside, footer). In app-shell on small screens the nav is drawn as a bottom bar but is still read before the main content; a skip link to <main> keeps that quick to pass.
  • Dashboard drawer. Closed, the nav is hidden from everyone (visibility: hidden), so focus cannot land on invisible links. The toggle must be a real <button> with a visible label; with the data-nav-open pattern, keep aria-expanded and aria-controls on it, close on Escape and on an outside tap, offer a close button inside the nav, and return focus. The popover pattern does all of this natively.
  • Motion. The drawer slides only when the user has not asked for reduced motion.
  • Sticky regions (data-layout-sticky) are capped at the viewport height and scroll on their own, so every link stays reachable; anchor jumps land below a sticky header (see data-sticky).

Why a body-level attribute (not a custom element)

A page shell is not a wrapper — it is the page. Wrapping the body's contents in a <page-shell> element would turn the header and footer into children of a generic element instead of the body. The attribute form keeps the document structure intact and adds the grid on top.
