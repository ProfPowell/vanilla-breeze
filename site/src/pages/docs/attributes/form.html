Overview

The form attribute names the id of the <form> a control belongs to. The control no longer needs to be inside that form: it can live in a sticky footer, a sidebar or another section, and it is still included in form.elements, FormData, validation and reset.

Applies to: form-associated elements: <input>, <select>, <textarea>, <button>, <output>, <fieldset>, <object>, and form-associated custom elements such as <combo-box> and <date-picker>.

Values

ValueForm owner
Attribute absentThe nearest ancestor <form>, if any (the default).
form="id" matching a <form>That form, wherever the control is. It overrides an ancestor form.
An id that doesn't exist, or isn't a <form>None. The control is not submitted with any form, even one it is nested inside.
Empty stringNone, for the same reason.

The value is an id, not a selector. Read the owner from script with control.form; it returns the owning <form> or null.

Examples

Fieldsets: set it on each control

form on a <fieldset> associates the fieldset itself, nothing more. Its children keep their own form owner, so they need the attribute too.

Notifications

The fieldset's own association matters only for form.elements and for disabled on the fieldset, which still disables every control inside it whatever their form owner.

Settings in a dialog

A <dialog> is ordinary DOM, so the simplest fix is to put it inside the form. Its fields are then submitted like any other.

Advanced settings

Use form="settings" on the dialog's fields only when the dialog has to live elsewhere in the page, for example at the end of <body>. commandfor and command open and close the dialog without script (Baseline 2025: Chrome 135, Firefox 144, Safari 26.2).

In Vanilla Breeze

  • VB's form helpers read form.elements, so remote controls take part: the data-validate coordinator's checks (src/lib/form-coordinator.js), data-show-when / data-wizard-if conditions (src/lib/form-conditions.js), the wizard and the form-reset sync used by enhanced controls.
  • A <form-field> outside the form element still shows its message on submit. The coordinator only looks for wrappers inside the form, but its checkValidity() fires invalid on the remote control, and the field listens for that event.
  • Remote submit buttons work with data-validate and data-loading: the coordinator and the loading state both use the event's submitter.

Accessibility

  • Form ownership is not exposed to assistive technology. Screen reader users meet a remote control where it sits in the DOM, not "in" the form, so place it next to the form and give it a label that makes sense on its own.
  • Tab order follows the DOM. A submit button in a footer far below the form is reached after everything between them.

Gotchas

  • A wrong id disconnects the control. A typo in form="..." removes the control from every form, including the one it is inside. Check control.form in the console.
  • Fieldset association doesn't cascade (see above).
  • The form and the control must be in the same tree: same document, same shadow root. It does not cross iframes or shadow boundaries.
  • Code that collects fields with form.querySelectorAll('input') misses remote controls. Use form.elements or new FormData(form).
  • Implicit submission (Enter in a text field) only uses buttons owned by the same form; a remote button with form="id" counts.

Which to choose

  • Nesting — the default. Put the control inside the form whenever the layout allows it.
  • form="id" — the layout forces the control elsewhere (sticky action bar, filters beside results).
  • Two forms — the controls really are separate submissions; don't share one control between them.
