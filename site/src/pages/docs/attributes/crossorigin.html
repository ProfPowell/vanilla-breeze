Overview

The crossorigin attribute switches an element's request from "no-cors" mode to CORS mode and says whether credentials (cookies, HTTP auth, client certificates) go with it. In no-cors mode a cross-origin file can still be used (a script runs, an image shows), but the page cannot inspect it. In CORS mode the server must opt in with Access-Control-Allow-Origin, and in return the page gets full access: integrity checks, readable canvas pixels, full error details.

Applies to: <script>, <link>, <img>, <audio> and <video>. Module scripts (type="module") and rel="modulepreload" are always fetched in CORS mode; the attribute only chooses their credentials mode.

There is no live demo on this page: what the attribute changes is a request header and a server response, which only show up with a second origin and in DevTools. The examples below show each case.

Writing just crossorigin is the same as crossorigin="anonymous".

Examples

Font preloads

Fonts are always fetched in CORS mode, even from your own origin. A preload must match the real request's mode to be reused, so a font preload needs crossorigin even for same-origin fonts. Without it the browser fetches the font twice. The stylesheet that declares the @font-face does not need it.

Third-party scripts with SRI

A cross-origin classic script with integrity but no crossorigin is blocked, because a no-cors response cannot be checked.

Script error details

Errors thrown by a cross-origin no-cors script reach window.onerror as just "Script error.", with no file, line or stack. In CORS mode the details are available, which error trackers need.

Reading pixels from a cross-origin image

Drawing a no-cors cross-origin image onto a canvas "taints" it: toDataURL() and getImageData() then throw a SecurityError. Load the image with crossorigin from a server that sends CORS headers.

Vanilla Breeze from a CDN

VB's CDN entry is a module script, so it is already a CORS request; unpkg and jsDelivr send Access-Control-Allow-Origin: *. Add crossorigin to the stylesheet link when you use SRI.

In Vanilla Breeze

  • VB has no styling hook for this attribute.
  • VB's runtime adds same-origin <link> elements for themes and packs (src/lib/theme-loader.js, src/lib/bundle-registry.js) without crossorigin. If you host dist/cdn/ on another origin, those requests are no-cors; that is fine for applying CSS but rules out SRI on them.
  • See integrity for which VB files an SRI hash covers.

Security

  • crossorigin does not bypass the same-origin policy; the other server decides by sending (or not sending) CORS headers.
  • Prefer anonymous. use-credentials sends the user's cookies to the other origin and requires it to trust yours explicitly. Use it only for authenticated assets on your own infrastructure.
  • If the server does not support CORS, adding the attribute makes the load fail; the browser does not fall back to no-cors.

Gotchas

  • Mismatched modes mean double downloads. A preload and the real request must agree on crossorigin (and its value).
  • Caches and Vary: Origin. If a server only sends CORS headers to some requests, a cached no-cors copy can be served to a CORS request and fail. Servers that answer CORS should send Vary: Origin or a constant Access-Control-Allow-Origin.
  • Same origin is not "ignored". For same-origin URLs the request still changes mode; it matters for font preload matching and for redirects to other origins.

Related

  • integrity — SRI requires CORS for cross-origin files.
  • rel — preload, modulepreload and preconnect (which also takes crossorigin).
  • referrerpolicy — the other per-request privacy control.
  • nonce — CSP for the scripts you load.
  • <link>, <script>, <img>, <canvas> — the elements.

Which to choose

  • Public CDN file with SRI, error tracking or canvas use — crossorigin (anonymous).
  • Any font preload — crossorigin, always.
  • Private asset that needs the user's cookies on another origin — use-credentials, with a server configured for it.
  • Plain images and media you only display — leave it off.
