Overview

data-wizard turns one <form> into a sequence of steps. Each <fieldset data-wizard-step> is a step; the wizard shows one at a time, validates it before moving on, skips steps whose data-wizard-if condition is false, and keeps a <progress>, a nav.steps list or a <progress-tracker> in sync. It is still one form with one submission.

Without JavaScript every fieldset is visible and the form submits as a single page.

For walkthroughs and layout recipes see the Wizard pattern; <form> covers the form features the wizard builds on.

    What the script does

    1. Collects the fieldset[data-wizard-step] elements in order.
    2. Marks the current step with data-wizard-active. Inactive steps are hidden by CSS because they lack that attribute; data-wizard-hidden is only for steps whose data-wizard-if condition is false.
    3. Wires Back / Next (or injects them), validates the current step before moving forward, and moves focus to the new step's <legend>.
    4. Hides the submit button until the last step. It is hidden, not disabled; pressing Enter in a text field before the last step means Next, never submit.
    5. Sets data-wizard-enhanced and the counter attributes on the form.

    Behaviour

    Validation

    • Next checks every enabled control in the current step with constraint validation, including form-associated components (combo-box, date-picker, star-rating …), and reports the first invalid one.
    • On submit, if the first invalid control is in another step, the wizard goes to that step and reports it instead of failing silently. This is how data-wizard-validate="none" forms validate. Calling form.requestSubmit() from script skips this routing.
    • Enter in a text field before the last step runs Next. On the last step it submits as usual.

    Conditional steps

    A step whose data-wizard-if is false gets data-wizard-hidden; it is skipped by Next and Back and not counted in the total. Its controls are disabled (the same contract as data-show-when), so its required fields never block submit and its values are not submitted. When the condition turns true, the controls the wizard disabled are enabled again; controls you disabled stay disabled.

    Conditions re-run on every input and change and after a reset. If script sets a value, dispatch an input event afterwards.

    Persistence

    data-wizard-persist saves the current step and field values through VBStore under vb:wizard:{form id}, as { step, data, session } with a timestamp. Saved state older than data-wizard-persist-hours (default 24) is ignored.

    • session: restored only in the same browser tab session (a per-tab id in sessionStorage is checked).
    • local: restored in any tab until it expires.
    • Never saved: passwords, type="hidden" (CSRF tokens, record versions), file inputs, buttons, autocomplete="off", credit card, one-time-code and new/current password fields, and anything marked data-autosave-ignore (on the control or a container). The same filter backs data-autosave.
    • On restore, read-only and author-disabled controls keep their server values. Restored controls dispatch input.
    • The saved state is cleared on submit from the last step, on wizardReset() and on form reset.

    Storage is localStorage: readable by any script on the origin and kept on shared devices until it expires. Mark anything sensitive with data-autosave-ignore.

    History

    With data-wizard-history, Next / Back / step-list clicks push #step=N entries; the browser Back and Forward buttons move between steps. A forward history move that fails validation puts the URL back on the current step. Initial load, condition changes and reset replace the entry instead of adding one.

    Step list: nav.steps or progress-tracker

    Both expect one <li> per step fieldset, in order. An empty list is filled from the legends.

    • nav.steps (no extra JavaScript): the wizard sets aria-current="step", data-completed and aria-disabled, makes completed items go back, hides items of skipped steps and runs a roving tabindex (arrows, Home, End).
    • <progress-tracker>: the wizard sets data-current to the step's data-step id (or position) and hides items of skipped steps. With data-clickable, clicking a completed step moves the wizard back. The tracker's "Step N of M" text counts every item, hidden ones included, so prefer it for wizards without conditional steps.

    Reset, insertion and clones

    A form reset returns to step 1 after the defaults are restored and re-evaluates conditions; a cancelled reset does nothing. Wizards inserted after load are enhanced. A cloned wizard (which copies data-wizard-enhanced) is enhanced on insertion, replaces the copied status region and reuses the copied nav.

    Events

    EventDetailFired when
    wizard:step-change{ from, to } (0-based, among included steps)After any step change.
    wizard:complete—The form submits from the last step (before your own submit handlers that were added later).
    wizard:reset—wizardReset() or a form reset.
    wizard:restore{ step, fields } (field names restored)Persisted state was applied after load.

    All events bubble from the form.

    const form = document.querySelector('[data-wizard]'); form.addEventListener('wizard:step-change', (e) => { console.log('Moved from step', e.detail.from, 'to', e.detail.to); }); form.addEventListener('wizard:restore', (e) => { console.log('Restored', e.detail.fields.length, 'fields on step', e.detail.step + 1); });

    JavaScript API

    • form.wizardNext() — next step after validating the current one; returns false when blocked.
    • form.wizardPrev() — previous step.
    • form.wizardGoTo(index) — 0-based index among included steps; validates when moving forward.
    • form.wizardReset() — back to step 1, clears saved state.
    • form.wizardController — the controller, with currentStep and totalSteps getters.

    These calls move focus to the new step only when focus is already in the wizard (or nowhere), so a call from elsewhere on the page does not steal it.

    Accessibility

    • After each step change focus moves to the new step's <legend> (given tabindex="-1"), so keyboard and screen reader users start at the step's name instead of on <body> when the button they pressed disappears.
    • A polite live region announces "Now on step 2 of 3: Profile" (data-label-status), and is not re-announced on every keystroke.
    • Inactive steps are display: none, so only the current step is in the tab order and the accessibility tree.
    • Skipped steps' fields are disabled, so validation never points at a field the user cannot reach.
    • nav.steps gets aria-current="step", completed items are named "Go to {name} (completed)", future items are aria-disabled, and arrows / Home / End move between items.
    • The <progress> element is a native progress indicator.
    • Without JavaScript every step is visible and the form submits as one page.
