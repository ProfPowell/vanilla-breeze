The approach

Vanilla Breeze starts from native HTML. A <button> is already focusable and announced, a <dialog> already contains focus, and a <details> already reports whether it is open. The library styles those elements and builds its components on them, so most accessibility comes from the markup and not from script.

The target is WCAG 2.2 Level AA. Three opt-in accessibility themes go further, to Level AAA contrast, larger text and targets, and a typeface made for legibility.

What is handled and what you provide

A library can make its own parts accessible. It cannot write your content. This table marks the line.

Area The library handles You provide
Keyboard and focus A visible focus ring on every control, the skip link style, focus containment in dialogs, arrow-key handling in each composite component The skip link itself, a source order that matches the reading order
Names, roles and announcements Roles and states inside each component, one shared live region for announcements, the .visually-hidden class Labels for controls, text alternatives for images, headings that describe their sections
Preferences and themes Reduced motion, increased contrast, reduced transparency and forced colors, all read from the system; three accessibility themes A way for readers to choose a theme, if you want one (<settings-panel> is ready made)
Color Semantic color tokens that meet AA contrast against their surfaces in light and dark, under every bundled theme Contrast for any color you add, and a second cue wherever color carries meaning
Forms Label, hint and error wiring through <form-field>; validation messages written into a live region A <label> for every control, and error text that says how to fix the problem
Language and direction Typography per script, right-to-left layout, locale-aware formatting lang on the page and on any passage in another language

Forms

Wrap each control and its label in <form-field>. The hint and the error are <output> elements. The component connects them to the control with aria-describedby, sets aria-invalid when validation fails and writes the message into the error output. Because that output is a polite live region, the message is announced when it appears.

We only use this to send your receipt.

The <form-field> page covers validation timing, grouped controls and custom messages.

What holds it in place

These checks run on every change to the library. A failure blocks the release.

Check What it catches
Markup conformance Skipped heading levels, form controls outside a <form-field>, <div> where an element with meaning exists, in every demo and documentation page
Contrast tests Text and control colors below AA, measured in a browser under each bundled theme in light and dark
Component tests Keyboard operation, focus movement, roles and states, right-to-left layout, reduced motion and forced colors
Manifest check A key or ARIA attribute listed in the tables on these pages that the component's code no longer contains
Resilience Matrix Records what each component does without JavaScript and without CSS

Automated checks find a minority of accessibility problems. Testing lists what to check by hand on your own pages.

Report a problem

If something in the library is hard to use with a keyboard, a screen reader, magnification or voice control, open an issue on GitHub and label it accessibility. Say which browser and assistive technology you used.
