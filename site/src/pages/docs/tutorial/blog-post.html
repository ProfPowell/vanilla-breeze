Tutorial: Blog post

Build a long-form article: a title and byline, five sections, a quote, a code sample, a chart, tags and a list of further reading. You'll write it as plain HTML, then add a reading width, two small custom elements and a generated table of contents.

About 15 minutes · Uses all four layers: semantic HTML, layout attributes, custom elements, web components

Before you start

Make a folder, and in it one file called index.html. Paste in this starter and open the file in a browser. Everything in the tutorial goes inside <body>.

A year of rain

The <link> is the whole install for the first three steps. The one line of CSS keeps the text off the edge of the window, using a Vanilla Breeze spacing token; it is the only CSS you will write. There is no script tag yet: you add it in step 4, the only step that needs it. For npm and self-hosting, see Quick Start.

Step 1 — Semantic HTML

An article is mostly decisions about meaning, and HTML already has an element for each one.

The post is an <article> with a <header> for the title and byline and a <footer> for what comes after the text. The date is a <time> with a machine-readable datetime. The quote is a <blockquote> whose own <footer> names the speaker. The code is <pre><code>. The chart is an inline SVG in a <figure> with a <figcaption>, so the file needs no image. The further reading is a native <details>, which opens and closes without any script.

Three smaller choices matter later. Each <h2> gets an id you chose, so a link to #results keeps working if you reword the heading. Each tag is a link with rel="tag", and the author link has rel="author": both say what the link is, and the stylesheet draws tag links as pills because of it. The opening paragraph has class="lead", one of a few variant classes Vanilla Breeze defines for cases where HTML has no element.

Field notes

A year of rain: what a backyard weather station taught me

By Mara Lindqvist · October 12, 2026 · 6 min read

Twelve months ago I bolted a rain gauge to the fence, mostly to settle an argument about whether our street gets less rain than the airport. It does. That turned out to be the least interesting thing I learned.

Why measure your own weather

The official station for our town sits at the airport, nine miles away and two hundred feet lower. Its numbers are accurate for the runway. They are a rough guess for my garden, which sits behind a ridge that splits most summer storms in two.

I wanted to know how rough. A gauge of my own would answer that, and it would tell me when the water butts were about to run dry instead of after.

The forecast tells you what the sky will do over the county. The gauge tells you what it did over your beans.

Ines Okafor, who has kept the allotment records since 1998

The hardware

The station is deliberately small. A tipping-bucket gauge counts rain in 0.2 mm steps, a sealed sensor reads temperature and humidity, and a single-board computer in a weatherproof box logs both every five minutes.

  • Tipping-bucket rain gauge, mounted level and clear of the fence line
  • Temperature and humidity sensor inside a louvred shield
  • Single-board computer, powered from the shed

The whole thing cost less than a decent pair of boots. The expensive part was the afternoon spent getting the gauge level.

Reading the gauge

Each time the bucket tips, a magnet closes a switch. The logger only has to count the pulses and multiply. This is the entire rain script:

MM_PER_TIP = 0.2
tips = 0

def on_tip(channel):
    global tips
    tips += 1

def rainfall_mm():
    return round(tips * MM_PER_TIP, 1)

A scheduled job writes rainfall_mm() to a file at midnight and resets the counter. Twelve months of data is a text file smaller than one phone photo.

What twelve months showed

The garden received 523 mm of rain over the year. The airport reported 640 mm. The gap is not spread evenly: winter totals match within a few millimetres, and almost all of the difference comes from four summer storms that passed north of the ridge.

July was the surprise. The airport logged 48 mm that month and the garden logged 9. The beans noticed before I did.

What I would change

I would mount the gauge on its own post from the start. For the first two months it sat too close to the fence, and a westerly wind was enough to shelter it. Those readings are marked as estimates.

I would also write the data down in two places. A power cut in March cost me three days, which I filled in from a neighbour's notebook. The notebook was right; the notebook is always right.

Check

  • The page is readable from top to bottom, and the quote, code block, caption and tag pills are already styled.
  • Click Further reading: it opens. That is the browser, not a script.
  • Make the window wide. The lines run the full width, headings sit tight against the text above them, and the tags are a bulleted list. Those are the three things step 2 fixes.

Step 2 — A reading measure with layout attributes

Long text needs a measure: a line short enough that your eye finds the start of the next one. It also needs rhythm, with more space above a heading than below it so each heading belongs to the text that follows.

data-layout="prose" does both. It caps the article at 65 characters per line, spaces its direct children, and gives the figure, the code block and the quote extra room. data-layout-centered puts the column in the middle of the page. You could get the width alone from data-layout="center" with data-layout-max="prose", but then you would have to space every heading yourself.

The rhythm reaches direct children only, so the lines inside the <header> and <footer> are still touching. Each becomes a stack with its own gap: tight in the header, where three lines form one unit, and looser in the footer. The tag list takes class="inline", the list variant that lays items out in a wrapping row without bullets. A layout attribute would arrange the items but leave the bullets, so the variant class is the right tool here.

What changed

  • The text sits in a centered column. Resize the window: the column stays the same width until the window is narrower than it, then it fills the space.
  • Headings have clear space above them, and the chart is a sensible size because it fills the column, not the window.
  • The tags are a row of pills, with a gap between them and the further reading.

Step 3 — Custom elements where HTML has no word

Custom elements in Vanilla Breeze are new tag names styled by the same stylesheet. The ones in this step have no JavaScript. The test for using one: is there a thing on the page that HTML has no element for, and that you would otherwise build from a <span> and a class?

This article has two. "Field notes" is a category label: not a heading, not a link, just a small chip. That is <layout-badge>; data-variant="subtle" and data-color="primary" give it a quiet tint that follows the theme. The byline gets a <user-avatar> showing the author's initials in a data-fallback span. The name is printed right beside it, so the avatar is marked aria-hidden="true" and a screen reader does not read "ML" before "Mara Lindqvist".

The tags fail the test, so they stay as they are. They are links, HTML has an element for links, and rel="tag" already makes them pills.

Step 4 — Web components: a table of contents and heading links

Web components are the layer that needs JavaScript, so the test is stricter: does the reader get something the first three layers cannot give, and is the page still whole without it?

A five-section article passes twice. A list of its sections helps a reader decide where to start, but a list written by hand goes stale the first time you rename a heading. <page-toc> builds the list from the headings on the page. It needs each heading to have an id, which is why you wrote them in step 1. levels="h2" limits it to the section headings and data-title sets its label. Its scope is a CSS selector and it reads the first element that matches. The default is main; main article says exactly which article you mean, so the list stays right when the page later gains a second one, such as a comment or a related post.

The second is sharing a section. <heading-links> adds a link icon to each heading it contains; activating one jumps to that section and copies its address. It goes around the <article>, not inside it. Inside, it would become the article's only direct child and the step 2 rhythm would have nothing to space.

Check

  • An "In this article" box lists the five sections. Click one: the page scrolls to it, the address gains #results, and that entry is marked as the current one.
  • In a window narrower than 64rem the box is a disclosure: click its title to fold it away. In a wider window it stays open.
  • Hover a section heading, or tab to it: a link icon appears. Click it and paste somewhere; you have the address of that section. On a touch screen the icons are always shown.
  • Turn JavaScript off and reload. The contents box and the link icons are gone and nothing is left in their place: you are looking at step 3. The headings still have their ids, so a link to #results still lands, and Further reading still opens.

What you learned

  • Start with the elements that say what each part is.
  • data-layout="prose" gives an article its measure and rhythm; nested groups such as the header and footer get their own stack.
  • Reach for a custom element when HTML has no element for the thing (<layout-badge>, <user-avatar>), and not when it does (tag links).
  • Add a web component when it gives the reader something new and the page is complete without it. <page-toc> and <heading-links> both leave step 3 behind when JavaScript is off.

Try it yourself

  1. Number the article. Add data-numbered to the <article> and see what happens to the headings and the figure caption. No script is involved. Read the article element.
  2. Show reading progress. Add a <reading-progress> element and scroll. Read reading-progress, then decide whether it passes the step 4 test for your page.
  3. Keep the contents in view. Move <page-toc> out of the article into an <aside> beside it, so the current-section marker is visible while you read. Read the sidebar section of page-toc and data-sticky.
