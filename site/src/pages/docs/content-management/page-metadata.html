Declare it in the head

A page states its author, dates, topics and license in <meta> and <link> tags. Components read those tags when they connect. You do not pass the same facts to each component as attributes.

The demo changes two tags and nothing else. The panel under the article is a <page-info auto>, which builds itself from the <head>. Open it to see the full record.

Where a standard name exists, the library reads the standard name: author, keywords, the Open Graph article properties, rel="license". Names that start with vb: are used only where no standard one fits.

The tags and who reads them

Every tag is optional. A component shows what it finds and leaves out the rest.

Standard names

TagValueRead by
<meta name="author"> The author's name <page-info>
<link rel="author"> or <meta property="article:author"> A URL for the author. The article:author value wins when both are present. <page-info>, as the author link
<meta name="last-modified"> A date, YYYY-MM-DD. article:modified_time is used when this is absent. <page-info>, <page-stats>
<meta property="article:published_time"> An ISO 8601 date <page-info>
<meta name="keywords"> Comma-separated terms <page-info>
<meta name="license"> and <link rel="license"> The license name and its URL <page-info>
<meta itemprop="version"> The version of this page <page-info>. <version-switcher> updates it after a swap.
<link rel="canonical"> The page's canonical URL The signature check, which includes the URL in what is signed

Library names

TagValueRead by
<meta name="vb:provenance"> human, ai-assisted or ai-generated, optionally followed by translated, synthesized or migrated, separated by spaces <page-info>
<meta name="vb:review"> unreviewed, fact-checked or editor-reviewed <page-info>
<meta name="vb:status"> draft, published or archived <page-info>. A badge appears in the summary line for any value other than published.
<meta name="vb:ai-tools"> Names of the tools used, as free text <page-info>
<meta name="concept">, repeated One topic id per tag <page-info>, which links each id to /topics/{id}/ (change the base with data-concept-base)
<meta name="vb:version-url"> A URL for this version's release note <page-info>, as the version link
<meta name="vb:versions-manifest"> The URL of a JSON list of this page's versions <version-switcher>, when it has no data-versions or data-src
<meta name="vb:hash">, <meta name="vb:signature">, <meta name="vb:signature-algorithm">, <link rel="author-key"> Written by a signing step <page-info>. See Document Provenance.
<meta name="vb:track-history" content="on"> Records visits to this page in the reader's own browser The history that <recently-visited> shows. <meta name="vb:no-track-history"> excludes a page.

The analytics module also collects every vb: tag and every concept tag on the page and attaches them to its events, so a tag you add for display is available for reporting too.

No component reads JSON-LD. If you publish a Schema.org Article block for search engines, keep it in step with the tags yourself.

Showing the metadata

Two components put these facts in front of the reader.

ComponentShowsSource
<page-stats> Reading time, word count and the last-modified date, in one line Counts the text of the element named by data-for. The date comes from last-modified.
<page-info> A summary line (author, date, provenance badge) that opens to a panel with author, history, how the page was made, and topics With auto, the tags in the <head>. Without it, the markup you wrote inside.

Two ways to use page-info

With the auto attribute the component builds its panel in the browser. That is the least markup, and the panel does not exist until the script runs.

Without auto, you write the panel as a <details> element inside <page-info>, usually from a template. It works before any script loads. The component then adds relative dates to each <time data-relative>, fills an element marked data-reading-time (counting the text inside any element marked data-signable), and sets the trust tier on the badge. Use this form when your build already knows the values. The <page-info> page has the full markup.

<page-info auto> reads the <head> once, when it connects. If a script changes a tag later, replace the element to render it again.

The site index

The components that list pages across a site (Finding Content) cannot read every page's <head>. They fetch one JSON file with a record per page. The library does not write that file. Your build does, from the same facts that go into the tags.

{ "url": "/guides/flu-vaccination/", "title": "Booking a flu vaccination", "author": "Tomas Okafor", "authorUrl": "/team/tomas/", "modified": "2026-11-03", "concepts": ["vaccination"], "provenance": "human", "review": "fact-checked", "status": "published", "signed": false }

The file is either an array of records or an object with a pages array. Each component uses a few fields and ignores the rest.

ComponentFields it reads
<author-index>author, authorUrl, title, url
<topic-map>concepts, title, url, plus a separate vocabulary file
<trust-filter>provenance, review, status, signed, title, url
<popularity-index>title and provenance, to label the pages its analytics endpoint returns

Generating the tags

Writing the tags by hand works for a few pages. Past that, generate them. This documentation site does it with a build plugin that turns front matter into tags, and a second that scans the built pages into /pages.json. Both plugins are part of this site's build, not of the vanilla-breeze package. They are short, and a good model for your own generator.

--- title: "Booking a flu vaccination" author: "Tomas Okafor" authorUrl: "/team/tomas/" published: "2026-06-18" lastModified: "2026-11-03" keywords: ["flu vaccine", "appointments"] concepts: ["vaccination"] provenance: "human" review: "fact-checked" license: "CC BY 4.0" licenseUrl: "https://creativecommons.org/licenses/by/4.0/" ---

The full list of tags, with the reasoning behind each name, is the meta-tag contract in the repository.
